2. AFTER OPTIMIZATION (With Indexes Created)

Indexes Created:
CREATE INDEX idx_products_fabric_type ON Products(fabric_type);
CREATE INDEX idx_orders_status ON Orders(order_status);
CREATE INDEX idx_payments_status ON Payments(payment_status);
CREATE INDEX idx_deliveries_status ON Deliveries(delivery_status);

Query A After Index:
EXPLAIN ANALYZE SELECT * FROM Products WHERE fabric_type = 'Ankara';

Result:
Bitmap Heap Scan on Products (cost=4.30..52.10 rows=124 width=210)
Recheck Cond: ((fabric_type)::text = 'Ankara'::text)
-> Bitmap Index Scan on idx_products_fabric_type (cost=0.00..4.20 rows=124 width=0)
Planning Time: 0.412 ms
Execution Time: 3.215 ms

Performance Improvement: 78.452 ms -> 3.215 ms (95.9% faster)
Reason: Index Scan instead of full table scan.

Query B After Index:

5. BRIEF PERFORMANCE ANALYSIS

The execution plans were analyzed using EXPLAIN ANALYZE to compare query performance before and after indexing.

1. Query on Orders Table (user_id = 10)*

- *Before Index (EVIDENCE3.png):* The query performed a `Seq Scan on orders` with a total cost of *94.50*. It had to scan the entire table and removed *4998 rows* by filter, which is inefficient for large datasets.
- *After Index (EVIDENCE4.png):* After creating `idx_orders_user_id ON orders(user_id)`, the planner used a `Bitmap Index Scan on idx_orders_user_id` with `Index Cond: (user_id = 10)`. The total cost reduced drastically to *18.45* and it only accessed *2 Heap Blocks* instead of full table scan.
- *Improvement:* Cost reduced by *80.4%* (94.50 -> 18.45) and data access changed from full table to direct index lookup, demonstrating effective query optimization.

2. Query on Products Table (fabric_type = 'Ankara')*

- *Before Index:* Cost was 78.452 ms with full table scan.
- *After Index (ExecutionPlans file):* Cost reduced to 3.215 ms using `Bitmap Index Scan on idx_products_fabric_type`.
- *Improvement:* *95.9% faster* execution (78.452ms -> 3.215ms).

Conclusion:Indexing significantly improves performance by avoiding sequential scans. The indexes created on `user_id`, `order_status`, `payment_status`, and `fabric_type` reduce query cost and execution time, making the database scalable.
